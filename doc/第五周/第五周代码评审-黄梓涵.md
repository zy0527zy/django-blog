## 二、评审发现与修改建议

### 1. comments：文章状态判断与注释不一致（建议优先确认）

- **位置**：`src/comments/views.py`，`CommentPostView.form_valid()`，约第 60～62 行。
- **现状**：判断条件为 `article.comment_status == 'c' or article.status == 'c'`，旁边注释说明“文章本身为关闭状态时，禁止提交”。
- **核对依据**：`src/blog/models.py` 的 `Article.STATUS_CHOICES` 只定义 `d`（草稿）和 `p`（已发布），而 `c` 是 `COMMENT_STATUS` 中“关闭评论”的取值。
- **问题**：`article.status == 'c'` 与当前文章状态枚举不一致，按现有常规数据取值不能起到限制未发布文章评论的作用；注释也容易让读者误解为存在文章状态 `c`。
- **建议**：由模块负责人先确认业务规则。如果要求仅已发布文章可评论，可评估使用 `article.status != 'p'`；无论是否改逻辑，都应同步把注释写准确。
- **性质**：原有业务判断疑点，**不能直接认定为本周代码标注引入的问题**。

### 2. comments：回复评论时未校验父评论属于当前文章（建议优先确认）

- **位置**：`src/comments/views.py`，`CommentPostView.form_valid()`，约第 76～80 行。
- **现状**：根据表单中的 `parent_comment_id`，调用 `Comment.objects.get(pk=...)` 获取父评论，再赋给当前评论的 `parent_comment`。
- **问题**：查询条件没有同时限制 `article=article`。如果提交了其他文章的评论 ID，现有代码没有在这一位置阻止错误的跨文章父子关联。
- **建议**：在查询父评论时同时核对所属文章，并根据业务规则处理不存在、不可见或不允许回复的父评论。提交前可补充对应表单/接口测试。
- **性质**：静态检查发现的潜在关联完整性风险；尚未用运行测试复现。

### 3. blog：`rebuild()` 名称容易让人误以为会清空旧索引（建议完善说明）

- **位置**：`src/blog/documents.py`，`ArticleDocumentManager.rebuild()`，约第 266～273 行。
- **现状**：方法调用 `ArticleDocument.init()`，再将本次获取的文章逐条 `save()` 到 Elasticsearch；未见先删除或清空原索引内全部旧文档的步骤。
- **问题**：目前注释称“重新建立 Elasticsearch 搜索索引”，可能让维护人员理解成完整清空并重建。仅从该方法的步骤，无法保证已经不在 MySQL 或不在本次文章集合中的旧搜索文档一定被清理。
- **建议**：若业务目标是“把当前文章同步写入索引”，应将注释改成更准确的描述；若目标确实是完整重建，则另行设计旧文档清理及失败恢复流程。
- **性质**：方法行为与说明的边界问题；未执行 Elasticsearch 实验，不断言一定存在脏数据。

### 4. blog：空文章集合会触发“全部文章”路径（建议明确）

- **位置**：`src/blog/documents.py`，`ArticleDocumentManager.rebuild()`，约第 269～270 行。
- **现状**：代码是 `articles = articles if articles else Article.objects.all()`，新补的中文注释已经说明“传入空集合时默认获取全部文章”。
- **问题**：注释与现行代码一致，但这一行为容易超出调用者预期：调用者本想传入空集合表示“本次不写入”，实际会变成处理全部文章。
- **建议**：先确认空集合是否应与 `None` 等同。若不应等同，后续可考虑使用 `if articles is None` 的明确判断，并补充空集合场景测试。本次仅作为后续优化建议，不要求为完成标注而改业务逻辑。
- **性质**：原有边界行为风险；不属于本周新增错误。

### 5. oauth：第三方账号与本地用户的关系说明还可更精确

- **位置**：`src/oauth/models.py`，`OAuthUser` 类说明及 `author` 字段，约第 9～20 行。
- **现状**：注释写“与本地 BlogUser 是可选绑定（0..1）的关系”；代码实际为 `ForeignKey(..., null=True, blank=True)`。
- **问题**：可选绑定这一点是正确的，但单写 `0..1` 容易让初学者误以为整个关系是数据库强制的一对一。`ForeignKey` 没有唯一约束时，同一个本地用户可以关联多条第三方授权账号记录。
- **建议**：注释补充“单条 `OAuthUser` 记录最多关联一个 `BlogUser`，可以为空；一个 `BlogUser` 可以关联多条 `OAuthUser` 记录”，与数据库实际约束保持一致。
- **性质**：注释准确性和关系重数表达的完善建议。

### 6. servermanager：机器人帮助中的默认对话服务描述与代码不符

- **位置**：`src/servermanager/robot.py`，`help()` 帮助文案约第 115～117 行，以及 `MessageHandler.handler()` 的普通消息处理逻辑。
- **现状**：帮助文本写“默认会与图灵机器人聊天”；普通非管理员消息实际经 `ChatGPT.chat(info)` 处理，`src/servermanager/api/commonapi.py` 调用的是 OpenAI 聊天接口。
- **问题**：帮助文案沿用了旧的服务名称，与现行代码不一致，容易误导使用者。
- **建议**：将文案改成不绑定具体厂商的“默认提供 AI 对话功能”，或者与实际所使用的接口名称保持一致。
- **性质**：用户可见文案过期，不是本周新增的程序缺陷。

### 7. djangoblog：搜索引擎推送范围的文件说明偏宽

- **位置**：`src/djangoblog/spider_notify.py`，文件开头约第 3～5 行及 `SpiderNotify.notify()`。
- **现状**：文件说明写“主动推送给百度等搜索引擎”；当前类中实现的是 `baidu_notify()`，统一入口也只调用此方法。
- **建议**：若目前仅支持百度，文件开头宜写“向百度主动推送文章 URL”；后续实际接入其他搜索引擎后再扩展说明。
- **性质**：注释覆盖范围与现有实现不完全一致，低优先级。

## 四、评审结论与后续安排

**结论：本次静态评审已形成可追踪的修改建议；注释基本有助于理解系统，但仍存在少量描述不准确、边界情况不清楚和原有业务逻辑风险。**

建议优先顺序：

3. **后续补测试**：索引空集合行为与删除旧文档场景（发现 3、4），并视课程后续周次安排验证。
