## 1. 软件系统概述

「栈外」是一款基于 Django 框架构建的个人技术博客系统，站名取意「栈里写码，栈外生活」，采用「技术 + 生活」双主题的内容定位，致力于解决个人知识沉淀与分享的需求。

### 1.1 系统定位

系统面向技术学习与生活记录两大场景，帮助博主以结构化的方式组织与发布内容：文章通过分类树（技术 → 后端开发 / 前端开发 / 数据库；生活 → 读书笔记 / 旅行）、标签、时间归档等多维结构进行管理，并提供全文搜索能力，使技术笔记与生活随笔都能被高效地沉淀、检索与分享。

系统基于 Django 5.2 的 MVT（Model-View-Template）架构实现，使用 MySQL 9.6 作为持久化存储，将文章、分类、标签、评论、用户、第三方授权等业务对象抽象为 24 张数据表。这些数据表及其之间的关联关系，正是本文档第 3 节数据模型设计的分析对象。

### 1.2 目标用户

| 用户类型 | 角色说明 |
|---|---|
| 博主（内容作者） | 系统的核心使用者，负责撰写、发布与管理文章，维护站点配置 |
| 访客（读者） | 浏览文章、按分类 / 标签 / 归档检索内容、发表评论与点赞的普通用户 |
| 站点管理员 | 通过 Django 管理后台统一管理文章、评论、分类、标签、用户与站点配置 |

### 1.3 核心价值

1. **内容沉淀与多维组织**：支持 Markdown 写作，通过分类树、标签、时间归档对文章进行多维组织，便于长期积累与回溯。
2. **高效的内容发现**：提供分类页、标签页、归档页、友链页与全文搜索等多类入口，读者可快速定位目标内容。
3. **互动与连接**：支持账号注册登录、第三方 OAuth 登录，以及评论、评论点赞、楼中楼回复，形成作者与读者之间的互动闭环。
4. **可扩展的插件体系**：通过插件机制（SEO 优化、阅读时长、图片懒加载、外部链接处理、版权声明等）在不改动核心代码的前提下按需扩展系统能力。
5. **便捷的运维管理**：内置 Django 管理后台，可对文章、评论、分类、标签、用户、站点配置进行统一管理。

## 2. 功能与数据分析

本节按照**功能—功能说明—主要数据对象**的统一口径描述软件功能。这里的数据对象指功能读取、创建、修改或关联的 Model / 实体；并非每个功能都需要新建数据表。

### 2.1 博客内容管理（blog）

| 功能 | 功能说明 | 主要数据对象 |
|---|---|---|
| 文章管理 | 创建、编辑与发布文章；保存标题、正文、时间和状态 | `Article`、`BlogUser` |
| 独立页面 | 使用 `Article.type` 区分文章和独立页面 | `Article` |
| 作者文章列表 | 按作者读取文章并展示列表 | `Article`、`BlogUser` |
| 分类管理 | 文章按分类组织，支持父子分类 | `Article`、`Category` |
| 标签管理 | 一篇文章关联多个标签，同一标签用于多篇文章 | `Article`、`Tag`、`blog_article_tags` |
| 阅读与归档 | 查看内容、记录浏览次数、按时间归档 | `Article` |
| 文章搜索 | 搜索已发布文章，索引基于文章信息 | `Article`（外部搜索索引为辅助存储） |
| 评论控制 | 按文章和全站设置评论开关及审核选项 | `Article`、`BlogSettings` |
| 友情链接 | 维护链接名称、网址、展示顺序和是否启用 | `Links` |
| 侧边栏管理 | 管理侧边栏自定义内容和顺序 | `SideBar` |
| 站点配置 | 维护站名、主题配色、SEO 和全局页面内容 | `BlogSettings` |

**主要数据关系：** `Article.author → BlogUser`、`Article.category → Category` 均为多对一；`Article.tags ↔ Tag` 为多对多；`Category.parent_category → Category` 为可选自关联。`Links`、`SideBar`、`BlogSettings` 无直接业务外键。

### 2.2 用户账户与权限（accounts）

| 功能 | 功能说明 | 主要数据对象 |
|---|---|---|
| 用户注册 | 接收注册资料，保存用户，部分注册流程需通过邮件激活 | `BlogUser` |
| 账户激活 | 校验激活信息并更新账户的激活状态 | `BlogUser` |
| 用户登录与退出 | 验证身份、建立或结束登录会话 | `BlogUser`、`django_session` |
| 找回密码 | 校验邮箱及验证信息，完成密码更新 | `BlogUser` |
| 作者身份与资料 | 保留用户名、邮箱、昵称、注册来源等信息 | `BlogUser` |
| 权限分配 | 用户关联用户组或直接关联权限 | `BlogUser`、`Group`、`Permission`、两张关联表 |

**主要数据关系：** BlogUser 可以发表多篇文章、评论及表情反应；BlogUser 与 Group、Permission 通过中间表构成多对多关系。登录 Session 是框架提供的会话存储，不是 BlogUser 的外键字段。

### 2.3 评论与互动（comments）

| 功能 | 功能说明 | 主要数据对象 |
|---|---|---|
| 评论发表 | 登录用户对文章提交评论 | `Comment`、`Article`、`BlogUser` |
| 楼中楼回复 | 通过父评论引用保存回复层级 | `Comment`（`parent_comment` 自关联） |
| 评论审核与展示 | 通过 `is_enable` 区分可展示、隐藏状态 | `Comment`、`BlogSettings` |
| 评论 Emoji 互动 | 用户对评论选择表情，再次操作可取消该类型表态 | `CommentReaction`、`Comment`、`BlogUser` |
| 互动统计 | 统计某条评论各表情数量及用户表态状态 | `CommentReaction`、`BlogUser` |
| 评论邮件辅助 | 源码提供评论和回复邮件通知辅助函数；是否自动触发取决于调用流程 | `Comment`、`BlogUser`、`EmailSendLog`（发送日志取决于实际邮件信号流程） |

**主要数据关系：** Comment 必须关联一篇 Article 和一个 BlogUser；父评论可为空；CommentReaction 必须同时关联 Comment 与 BlogUser。评论表情的唯一性以 `(comment,user,reaction_type)` 联合约束保障。

### 2.4 第三方登录与账号绑定（oauth）

| 功能 | 功能说明 | 主要数据对象 |
|---|---|---|
| 第三方平台配置 | 维护平台类型、AppKey、AppSecret、回调地址与启用状态 | `OAuthConfig` |
| 授权登录 | 跳转第三方平台，接收回调、令牌及用户资料 | `OAuthConfig`、`OAuthUser` |
| 第三方身份留存 | 保存 openid、昵称、来源平台及可选邮箱等信息 | `OAuthUser` |
| 本地账户关联 | 将第三方身份与本地博客账户关联，必要时要求邮箱确认 | `OAuthUser`、`BlogUser` |

**主要数据关系：** `OAuthUser.author_id → BlogUser.id` 是**允许为空的多对一外键**；不能写成数据库强制一对一。OAuthConfig 与 OAuthUser 通过平台类型发生业务层对应关系，数据库表中**没有二者之间的外键**。

### 2.5 运维与系统服务（servermanager）

| 功能 | 功能说明 | 主要数据对象 |
|---|---|---|
| 命令记录管理 | 保存预定义命令标题、文本和描述 | `commands` |
| 邮件发送记录 | 保存邮件收件人、标题、内容和发送结果 | `EmailSendLog` |
| 微信消息机器人 | 提供关键词搜索、分类列表、近期文章等消息响应 | `Article`、`Category`；会话缓存 / 文件存储 |
| 管理员命令操作 | 使用管理员状态与密码校验流程处理命令执行请求 | `commands`；微信会话数据 |
| 普通消息对话 | 尝试调用外部对话 API 返回文本；依赖环境中的 API 配置 | 主要使用会话数据，不要求新增业务表 |

**实现边界：** 微信机器人源码中的 `weather:` 和 `idcard:` 当前仅返回“建设中”；帮助文本提到的部分命令未发现对应处理函数，故不应将其宣称为已实现功能。`commands` 和 `EmailSendLog` 两表本身**均无外键**。

### 2.6 系统级管理与基础支撑

| 功能 | 功能说明 | 主要数据对象 |
|---|---|---|
| 后台管理 | 自定义 AdminSite 注册各业务模型，操作文章、用户、评论等 | 业务 Model、`LogEntry` |
| 角色权限 | 利用用户组与权限项限制操作能力 | `BlogUser`、`Group`、`Permission` |
| 会话维护 | 保存登录相关会话数据及失效时间 | `django_session` |
| 站点信息 | 提供站点域名与名称 | `django_site` |
| 模型类型登记 | 为权限及管理日志标识模型所属应用及名称 | `django_content_type` |
| 数据库迁移 | 记录已执行的数据库迁移 | `django_migrations` |

### 2.7 主要业务过程与对象流转

1. **文章发布：** 管理员选择作者与分类，保存 `Article`，再通过 `blog_article_tags` 关联若干 `Tag`。浏览与搜索时以已发布文章为主要查询对象。
2. **评论互动：** 用户通过 `BlogUser` 身份发表关联 `Article` 的 `Comment`；回复保存 `parent_comment`；表情操作创建或删除 `CommentReaction` 记录。
3. **第三方登录：** 使用 `OAuthConfig` 对接授权平台，将第三方身份保存在 `OAuthUser`，其 `author` 字段在本地账户绑定前允许为空。
4. **权限控制：** 用户与组、权限的关联存储在两张中间表；权限项再关联 `ContentType`，共同支持 Django 后台授权体系。

“栈外”博客系统数据库整体 E-R 图。图中按功能划分为博客内容、用户与权限、评论互动、第三方登录、服务器管理、Django 权限系统及 Django 内置表七个模块；每个实体框展示数据表及其主要字段，标记 PK 的字段为主键，FK 的字段为外键，虚线表示可选关联。底部汇总了 20 条外键关系及重数对照。整体上，文章关联作者、分类和标签，评论支持作者、互动记录及父子回复，用户与用户组、权限之间通过关联表实现多对多关系；分类支持父子层级，第三方登录账号可关联博客用户。

### 3.2 实体与数据库表结构

**字段表阅读方法：** 下列字段类型使用第五周最终版 MySQL `CREATE TABLE` 导出结果；PK 为主键，FK 为数据库实际存在的外键，其余用“—”表示。部分字段的“允许 NULL”在说明列单独标出。`Model` 指 Django ORM 中相应的模型类；中间表是 ORM 自动生成的关联模型，并不要求有独立业务类。

### 3.3 主外键关系、重数与关系名称

以下列出数据库导出中实际存在的 20 条外键。重数从**被引用的一方 → 引用的一方**表述，通常为 1:N。数据库外键可空的关系另外标注。特别地，多对多需要通过两条外键分别展开，不是数据库中直接存在的“多对多外键”。

| 3 | `blog_category` | `blog_category.parent_category_id` | 0..1 : N | 分类层级（可空自关联） |

| 7 | `auth_group` | `accounts_bloguser_groups.group_id` | 1 : N | 组包含用户 |
| 8 | `accounts_bloguser` | `accounts_bloguser_user_permissions.bloguser_id` | 1 : N | 用户拥有直接权限 |
| 9 | `auth_permission` | `accounts_bloguser_user_permissions.permission_id` | 1 : N | 权限授予用户 |
| 10 | `blog_article` | `comments_comment.article_id` | 1 : N | 文章包含评论 |

| 15 | `accounts_bloguser` | `oauth_oauthuser.author_id` | 0..1 : N | 第三方身份可选绑定用户 |

- `Article` 与 `Tag` 为 N:M，经 `blog_article_tags` 实现；`BlogUser` 与 `Group`、`Permission` 也通过中间表实现 N:M。
- `OAuthUser.author_id` 可以为空，而且不是唯一外键，因此**不应**写为 `OAuthUser` 与 `BlogUser` 数据库级 1:1。
- `OAuthConfig.type` 与 `OAuthUser.type` 在业务上表示第三方平台，但**无数据库外键**。

### 3.5 约束与一致性说明

1. **实体标识：** 大多数表使用数值型自增 `id` 主键，`django_session` 则使用 `session_key`（varchar(40)）作为主键。
2. **唯一性：** `blog_article.title`、分类和标签的 `name`、部分顺序字段、用户的 `username` 及多个关联中间表组合键设置了数据库级唯一约束；评论表情记录以 `(comment_id,user_id,reaction_type)` 唯一约束避免重复。
3. **可空性：** 分类父节点、评论父节点、第三方账户对应的本地用户允许 NULL；其余关系应参照实际 SQL 判断，不应把“业务可选”一概写为“数据库可空”。
4. **数据类型：** Django 的 `TextField(max_length=300)` 最终对应 MySQL `longtext`，其中 `max_length` 并不等于数据库物理列长度；`BooleanField` 在本次导出中对应 `tinyint(1)`。
5. **模型校验与数据库约束不同：** `BlogSettings.clean()` 检查单实例配置，`OAuthConfig.clean()` 检查平台类型重复；两项均不能直接等同于数据库级 `UNIQUE` 约束。
6. **模型类命名：** `servermanager.commands` 源码类名为全小写 `commands`，文档与当前源码保持一致，不擅自改成 `Commands`。
