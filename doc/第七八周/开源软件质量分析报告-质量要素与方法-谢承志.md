## 2.1 分析的软件质量要素

依据 ISO/IEC 25010 软件质量模型，结合本项目实际情况，本次分析重点关注以下质量要素。

### 2.1.1 内部质量要素（代码自身的静态属性）

| 质量要素 | 关注内容 |
|---|---|
| **可维护性** | 代码结构是否清晰、模块化是否合理、注释是否充分、命名是否达意 |
| **编码风格规范** | 是否遵循 PEP 8（缩进、行宽、空行、导入顺序、命名等） |
| **设计质量** | 是否符合单一职责、开闭原则、高内聚低耦合、信息隐藏等设计原则 |
| **可读性** | 变量 / 函数 / 类命名、注释质量、代码块组织是否便于他人理解 |
| **复用性** | 公共能力是否抽象为基类 / Mixin / 工具函数，避免重复实现 |

### 2.1.2 外部质量要素（代码运行时的行为属性）

| 质量要素 | 关注内容 |
|---|---|
| **正确性 / 功能性** | 核心业务流程（注册、登录、OAuth 授权、评论、搜索等）是否正确实现 |
| **健壮性 / 容错性** | 对外部依赖（第三方接口、缓存、邮件）的异常处理与兜底是否到位 |
| **安全性** | 开放重定向、XSS、Cookie 属性、SQL 注入、越权等常见 Web 安全问题的防护 |
| **性能 / 效率** | 数据库查询是否高效（N+1、缺索引）、网络请求是否设置超时、是否不必要的缓存穿透 |
| **可测试性** | 代码是否便于单元测试，测试是否隔离外部依赖 |

> 本次分析以**内部质量**（人工精读 + 静态工具分析）为主，辅以**外部质量**（人工阅读关键路径 + 单元测试）判断。

## 2.2 软件质量分析方法

本次分析采用「人工分析 + 工具分析」相结合的方式，覆盖代码的静态与动态两个维度。

### 2.2.1 人工分析（内部质量 + 外部质量）

- **代码精读（走查）**：每人精读自己负责 app 的全部代码，逐模块 / 函数 / 关键代码块阅读，按 3.1~3.4 四个维度（代码风格、代码设计、编程技能、代码质量问题）形成分析结论。
- **注释标注**：在精读过程中以 `#姓名缩写:` 打头补充模块级、函数级、核心代码块注释，标注人可追溯。
- **缺陷走查**：重点检查安全（重定向校验、Cookie 属性）、健壮性（异常捕获、超时、事务）、性能（缓存、查询）等关键路径，逐条记录并判断是否修复。
- **测试验证（外部质量）**：运行 / 编写单元测试，验证核心业务逻辑的正确性；外部依赖用 mock 打桩隔离。

### 2.2.2 工具分析（内部质量）

| 工具 | 分析维度 | 说明 |
|---|---|---|
| **Ruff** | 未使用名称、导入排序、命名规范、现代写法、行长、复杂度 | 速度快，自动修复能力强，`ruff check --fix` 可批量修复 |
| **Flake8** | PEP 8 风格、注释空格、文件末尾换行、圈复杂度 | 与 Ruff 互补，发现 E/W 类风格问题 |
| **Pylint** | 更深层的代码味道、接口规范 | 可选，用于二次确认 |
| **VS Code 扩展**（Ruff / Pylint / Flake8） | 单文件实时检查 | 边写边改，即时反馈 |
| **GitHub Actions** | 全项目质量检查 | 提交时自动跑工具，拦截明显问题 |

- **执行方式**：命令行对项目 / 单 app 执行（如 `ruff check src/oauth`、`flake8 src/oauth`），工具配置在根目录 `ruff.toml` / `.flake8`，统一行宽 120，排除虚拟环境与生成物。
- **修复闭环**：工具发现问题 → 能自动修复的用工具 `--fix` → 需人工判断的手动修复 → 在报告中注明「是否完成修复」。

> 说明：`#姓名缩写:` 注释触发 Flake8 `E265` 属规则冲突，已在 `.flake8` 中项目级豁免，不计为缺陷（详见 oauth 部分 3.1）。
