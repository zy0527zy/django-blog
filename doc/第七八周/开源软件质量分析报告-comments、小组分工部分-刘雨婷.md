## 3. 人工分析代码的质量情况：comments

### 3.1 代码风格

comments 模块按 Django 应用结构组织，包含模型、视图、表单、模板标签、后台管理、URL 和邮件通知等代码。多数核心模型和视图已有说明性注释，`CommentPostView`、`CommentReactionView` 等类视图按功能区分了评论提交与表情反应接口。静态检查发现部分旧式字符串格式化、导入顺序和行尾空格问题，说明代码风格仍有统一空间。

### 3.2 代码设计

`Comment` 模型通过外键关联用户和文章，并通过指向自身的 `parent_comment` 支持楼中楼；`CommentReaction` 单独保存用户对评论的表情反应，并用联合唯一约束避免同一用户对同一评论重复创建相同表情。评论表单只开放正文输入，作者、文章和父评论由视图关联；评论发布和反应接口分别处理页面跳转与 JSON 响应，职责边界较清楚。

`get_reactions_summary` 会按表情统计并查询用户信息，`parse_commenttree` 会递归查找子评论。当前写法便于理解功能；若评论量或嵌套层级增加，后续可结合实际查询情况评估数据库访问次数，再决定是否批量查询或优化，暂不据此认定为已确认缺陷。

### 3.3 编程技能

模块使用 Django ORM 表达评论、文章、用户及父子评论关系，并通过数据库索引支持常见评论查询。视图使用 `get_object_or_404` 处理评论和文章查找，反应接口校验允许的表情类型，并使用 `get_or_create` 实现添加或取消反应；查询反应用户时使用 `select_related('user')`，减少逐条读取关联用户的查询。

Ruff 当前统计中的 `I001` 是导入排序/格式问题，`UP025` 是 Python 3 字符串前多余的 `u` 前缀，`UP031` 是旧式 `%` 格式化建议，`W291` 是行尾空格。Ruff 标记有 `[*]` 的项目可由普通 `--fix` 尝试修复；本次未在合并尚未提交的工作区运行自动修复。Flake8 的两项 `W291` 与 Ruff 的两项 `W291` 是同一位置的问题，不是额外的两项。

Pylint 的 `E1101` 对 Django ORM 的 `Model.objects` 可能是未加载 Django 插件导致的误报，暂不作为已确认代码缺陷；`C0415` 需要结合局部导入原因审查；`C0209` 可在确认格式行为不变后评估改成 f-string；`C0114` 可通过增加模块说明字符串处理。上述项目暂未全部修复，避免仅为提高工具评分而扩大改动范围。
