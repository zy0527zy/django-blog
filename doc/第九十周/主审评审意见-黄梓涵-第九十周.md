## 一、总体评审结论

本轮维护覆盖 `djangoblog`、`blog`、`accounts`、`comments`、`oauth` 和 `servermanager` 六个主要子系统。

各模块总体沿用 Django MVT、ORM、Admin、中间件及现有插件机制开展功能扩展，主要维护内容与课程任务分工相对应。

**主审结论：有条件通过。**

主要依据：

1. 六个子系统均有明确的功能维护方向，功能与所属模块基本对应。
2. blog、accounts、comments、oauth 和 servermanager 的维护工作围绕各自既有业务模块展开，没有必要地重建整套业务架构。
3. blog 通过复用原有 `Article.views` 和 `Article.article_order` 字段，降低了重复数据结构带来的维护成本。
4. 各模块已有相应测试代码或历史测试记录，但不能将历史测试结果直接认定为当前评审基线的最新测试结果。
5. OAuth 回调安全、邮件重试并发幂等和部分统计口径仍需要持续核实。

本意见属于课程项目主审意见，不替代教师验收、完整部署测试或 GitHub PR 正式评审。

### 2.5 oauth 子系统（谢承志）

**主要维护内容**

- 新增 Gitee 第三方登录管理器。
- 将 Gitee 接入原有 OAuth 管理器选择机制。
- 修复 GitHub OAuth 授权回调地址构造问题。
- 使用后台配置的 `callback_url` 保持授权请求与令牌交换阶段的回调地址一致。

**值得肯定**

- Gitee 复用 `BaseOauthManager`，延续现有 OAuth 架构。
- GitHub 回调地址修复针对原有地址构造问题进行处理。
- 沿用统一 OAuth 登录和用户绑定流程。

**需要重点复核的安全问题**

此前静态审查记录提出以下问题。由于这些结论来自旧审查快照，当前状态需要以本次评审基线的源码复核，不应未经验证直接认定为仍然存在或已经解决。

1. **OAuth state 校验：** 核实授权发起时是否生成随机、一次性 `state`，是否与当前会话关联，以及回调时是否验证并消费。
2. **next_url 保存：** 核实登录前的跳转目标是否经过安全校验并在授权往返过程中可靠保存，避免回调后丢失原始目标或发生不安全跳转。
3. **回归测试：** 核实 state 缺失、不匹配、回调地址一致性、第三方用户信息读取和安全跳转等测试证据。

**评审意见：有条件通过；OAuth 回调安全检查应作为优先复核事项。**

- 扩展邮件发送日志，记录失败原因及重试信息。
- 新增 `EmailService`，统一处理失败邮件重试。
- 新增 `retry_failed_emails` 管理命令。

**值得肯定**

- 统计逻辑集中于服务类，视图负责权限检查及页面渲染。
- 后台统计页面设置了管理员访问限制。
- 邮件重试复用服务层，避免后台操作和管理命令重复实现发送逻辑。
- 测试使用 mock 隔离 SMTP 外部依赖。

**主审建议**

- 复核同一失败邮件被后台操作和管理命令同时处理时的并发重复发送风险。
- 复核热门文章统计是否需要区分普通文章与页面型内容。
- 外部 ChatGPT 接口测试应避免依赖真实密钥、网络和额度，优先通过 mock 隔离。

**评审意见：基本通过，邮件重试并发幂等及统计筛选口径列为持续改进事项。**
