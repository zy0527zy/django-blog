## 二、评审发现与建议

### R1. comments：测试说明需要区分“包含测试”与“已经验证防护”

- **位置**：`837aeec` 的 `src/comments/test_views.py` 文件头，以及 `CommentSecurityTest.test_xss_protection()`、`test_sql_injection_protection()`。
- **现状**：新文件头列出 XSS、SQL 注入防护测试。XSS 测试提交输入后，主要断言重定向和评论对象存在，没有检查页面输出中脚本是否已转义；SQL 注入测试主要检查响应范围和评论记录存在。
- **问题**：这些断言可以说明当前测试执行了相关输入场景，但不足以证明完整防护效果。文件头不是新增防护实现，报告或答辩不宜将其解释为“安全验证通过”。
- **建议**：在说明中明确“相关输入场景的基础测试，渲染转义等效果仍需专门断言”；后续可检查最终 HTML 的转义结果和数据库结构完整性。
- **性质 / 优先级**：本周说明的验证范围边界，P2；弱断言原本已存在，不认定由标注引入。

### R2. comments：调用邮件函数不等于已验证实际投递

- **位置**：`837aeec` 的 `src/comments/tests.py` 末尾，新增“验证评论邮件通知可正常调用”的注释。
- **现状**：调用 `send_comment_email(comment)`，没有在此处检查邮件内容、收件人、发送结果或邮件 outbox。
- **问题**：测试覆盖的是函数调用路径；即便测试正常结束，也不能据此证明邮件成功投递。
- **建议**：保留“可正常调用”的有限表述，在报告中不要扩展成“邮件发送成功”；若补测试，可使用测试邮件后端及明确的 outbox 断言。
- **性质 / 优先级**：验证声明提醒，P3；当前注释的有限表述本身可保留。

### R3. servermanager：`assertIsNotNone()` 不保证返回内容非空

- **位置**：`8b3c288` 的 `src/servermanager/tests.py`，`test_chat_gpt()` 和综合测试中的同类断言。
- **现状**：`self.assertIsNotNone(content)` 新注释写“断言返回内容不为空”。
- **问题**：该断言只排除 `None`，空字符串、空列表等仍可通过。将其描述为“非空”会高估测试强度。
- **建议**：本周先把注释改为“断言返回值不是 None”；如果业务需要有效文本，后续另加类型与去空白后长度的断言。
- **性质 / 优先级**：本周新增注释准确性，P2；业务测试逻辑未被本周修改。

### R4. djangoblog：只读后台不能保证日志在所有途径下不可篡改

- **位置**：`a757a7e` 的 `src/djangoblog/logentryadmin.py` 模块说明和权限方法。
- **现状**：说明写“保证操作记录可追溯、不可篡改”；代码禁止后台新增、删除，限制修改权限的 POST，并移除批量删除 action。
- **问题**：这些措施约束该管理界面的操作，未覆盖数据库直连、其他 ORM 调用或外部写入途径，因此“不可篡改”表述过强。
- **建议**：改为“在该后台管理界面中只读展示，限制手动修改与删除，便于追溯”。不可篡改审计若确有需求，应另设计存储和完整性措施。
- **性质 / 优先级**：本周新增说明的保证边界，P2。

### R5. accounts：移除并新增时间字段不等同于保留数据的改名

- **位置**：`fec6020` / `ec30b72` 的 `src/accounts/migrations/0002_alter_bloguser_options_remove_bloguser_created_time_and_more.py`。
- **现状**：总注释提到更新字段名称；迁移实际使用 `RemoveField(created_time / last_mod_time)`，随后 `AddField(creation_time / last_modify_time)`，没有 `RenameField` 或复制旧值的数据迁移。
- **问题**：逐项“移除旧字段 / 添加新字段”的注释正确，但总说明可能让读者以为旧时间数据被自动保留。静态代码不能支持这一保证。
- **建议**：总说明补充“通过删除旧字段并增加新字段实现结构调整，未在本迁移中复制历史时间值”；本周不为了注释作业重写已经执行过的历史迁移。
- **性质 / 优先级**：本周说明完整性，P3；原迁移逻辑未变，未进行数据库实验。

### R6. blog：详情访问的发布状态限制需要单独确认

- **位置**：`src/blog/views.py`，`ArticleDetailView`。
- **现状**：模型为 Article，按 `article_id` 获取对象；未重写查询集以限制 `status='p'`。
- **问题**：从当前类的实现不能断言草稿详情不可访问，与首页等列表的已发布过滤并不相同。
- **建议**：本周用例说明和注释明确这一实际边界；后续由负责人与组长确认是否应限制未发布详情，再另行实施和测试。
- **性质 / 优先级**：原有业务边界，自查记录，P2；本周只补注释，未改逻辑。

### R7. blog：批量发布与逐个模型保存的副作用不同

- **位置**：`src/blog/admin.py`，`makr_article_publish()`；对照 `djangoblog/blog_signals.py`。
- **现状**：批量 action 使用 `queryset.update(status='p')`，而缓存处理依赖模型保存接收器等路径。
- **问题**：不能将批量更新画成必然调用 `Article.save()` 或触发 `post_save`；不能仅根据已有信号保证该 action 后缓存和索引立即一致。
- **建议**：本周模型图说明区分两条路径；一致性需求后续另行核对，不以完成标注为由扩大业务修改范围。
- **性质 / 优先级**：原有副作用边界，自查记录，P2。
